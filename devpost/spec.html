acu-primer

One Cloudflare project in three pieces: a Svelte app in the browser, a Worker for /api/, and a D1 database. Claude Opus 5.5 writes the drafts, and nothing it writes reaches a student before sign-off.

The pieces, and a journey through them

Step through the PRD's core journey. The pieces and arrows each step uses light up.

In plain language

The app in the browser is written in Svelte and holds both the player and the author side. It's one page, so moving between modules never reloads. A service worker keeps a copy of the app and every course a student has opened, so the player works offline. Progress and unsent events sit in localStorage.

The Worker answers everything under /api/: courses, events, sign-off, and calls to Claude. It holds the API key, so the key never reaches a browser.

D1 is the database: courses, lessons (one JSON document each), sign-offs and events.

It's the smallest setup that gives a link, a database, a secret key and offline play, and Cloudflare's free tier covers all of it. The budget goes to Claude.

What could break, and what happens

Claude's JSON doesn't fit, or it refusesOne retry with the error, then "Try again" for the author. Nothing half-valid is saved.
The Worker hits 10ms of CPUPages are uploaded once and streamed through. Measured early. If needed, the $5 plan.
A long draft and a closed tabThe draft is lost, so start again. If drafts routinely take minutes, Workflows comes later.
Offline, and the course was never opened"Open this course once with a connection."
Events can't be sentThey stay queued, and the student notices nothing.

A question worth understanding

Where do published lessons live?

The explainer puts course JSON in static files. That works for files that exist at deploy time. But the tool creates and signs off lessons while the app runs, and static files only change with a deploy. So lessons live in D1 and come from GET /api/courses/:slug. Offline still works, because the service worker keeps that response. The cost is one small D1 read per course load. Hand-written lessons go in through the same door, via scripts/import-lesson.ts.

Isaac asked: is offline still possible?

Yes. The browser never talks to D1. It only sees the JSON response from GET /api/courses/:slug, the same as a static file would be. The service worker saves that response on the first online visit and hands it back when there's no network. The response carries every visible lesson in full, so one visit caches the whole course. A lesson signed off or edited later appears at the student's next online visit.

Decisions and open issues

Isaac's decisions
  • Svelte 5 + Vite, no SvelteKit. It reads like templates and is small for cheap phones. Agents know React better.
  • Opus 5.5 for drafting, with Sonnet 5 as a manual backup (DRAFT_MODEL)
  • Send the section's pages as a PDF: formulas and figures survive, at more tokens per page
  • From the notes: all Cloudflare, TypeScript, deployed to a link, Access (or a passphrase) as the only login
Details that follow from those (open to change)
  • Lessons in D1, served by the Worker
  • Pages sent to the Files API once, then referenced by id
  • vite-plugin-pwa for the service worker; localStorage for progress and events
  • A device id on every event
  • Structured outputs plus a Zod check, with one retry
Open issues, checked early in the build
  • Can Access cover only the author paths on workers.dev? If not, use the passphrase.
  • Worker CPU time with PDF uploads
  • The authoring flow's steps, after the baseline lesson
  • What counts as a "simpler question"
  • How long a draft takes
  • OpenIntro's exact section pages
  • Devpost disclosure of any pre-Sep-22 work
